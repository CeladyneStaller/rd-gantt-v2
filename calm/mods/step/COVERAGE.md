# Current step and logic trees (X-exp): coverage

Scope: inv/exec.md §18 (Current step), §20 (Outcome recorder), §21 (Logic-tree manager), §22 (embedded ETB),
the experiment side of §19 (Connect data for an experiment) and the ETB / current-step items of §24;
inv/sales.md §16, §17 and the ETB caveats of §21–22.
Files: `mods/step/` (Current step panel, recorder, tree manager, Overview card: `mod.js`, `slot-exp.html`,
`part-val.html`, `slot-sheets.html`, `slot-ov-side.html`, `mod.css`, `seed.js` analysis runs) and `mods/etb/`
(the logic-tree editor: `mod.js` with today's ETB core ported verbatim, `slot-exp-tree.html`, `slot-sheets.html`,
`part-result.html`, `mod.css`, `seed.js` trees). Scenarios: `test/sc_exp.js` (both boards).

`[x]` done · `[~]` changed (says why) · `[ ]` not done · "fixed:" = today's bug or dead path; the intended behaviour is built.

Storage rule used everywhere: `doc.etbTrees[objectiveId]` is the multi-tree container `{ schema:2, trees:[…], activeTid }`.
Every edit goes through `ETB.edit(C, ctx, tid, fn)`, which changes one tree in its own slot inside one `C.mutate`.
A legacy bare tree (schema 1, e.g. Fuel Cell's AST tree) is read as one tree "Main" (`RD.etbTreesOf`) and written back
as a container on its first edit, keeping every field. Nothing ever replaces the container with a bare tree.
